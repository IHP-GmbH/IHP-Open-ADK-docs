.. _shared_data:

Where shared data lives
=======================

.. include:: /common.inc

Several repositories make up the toolchain, and some of their files are read by
the others: a rule value, a method's pitch, a layer sheet, a die's pin list.
This page says, for each of those files, which repository owns it, where it
is, what schema checks it, how its version is stated, and which other
repositories read it. Each row links the page that documents the datum itself.

.. note::
    The tables are generated by ``docs/scripts/gen_shared_data.py`` and checked
    against the code this release pins. Each owner's file and schema has to
    exist at the pin, a version is read from the file, and each reader file
    named here has to still name the datum. When a row stops matching the
    code, the build stops. A tool that reads a file only to verify it counts
    as a reader. Readers in tools that are not public yet
    (``interposer-pnr``, ``packaging-flow``, ``assembly-lvs``,
    ``chiplet-cosim``, ``chiplet-flow``) are checked at the commits the
    ADK-Tools image stages when the documentation is regenerated for a
    release.

Why the data is not in one place
--------------------------------

The ADK keeps only its own assembly rules. Each PDK publishes its own data
with its own release: the interposer PDK its stack, rule values, layer sheet
and routing descriptors, the interconnect PDK its methods. A new technology
therefore brings its own package, and the ADK does not change for it. Every
datum has exactly one owner. Where another repository holds a copy, the last
table says what holds the copy to the owner's file, and says so when nothing
does.

The ADK's internal registries, read only by the ADK itself, are on
:doc:`/adk/09_registries`.

Copies and what keeps them equal
--------------------------------

A copy of another repository's file, and the check that holds it to the
owner's. A path written ``a{b,c}`` names two files, ``ab`` and ``ac``.
Some are listed in ADK-Tools' ``ci/contract-registry.json``, which its
contract gate reads; the others are held by the copying repository's own tests
or by an ADK-Tools check. A check marked "at image build" runs on the staged
trees when the ADK-Tools image is built, not in continuous integration, which
has no staged trees.
